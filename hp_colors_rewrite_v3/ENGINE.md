### Native health-layer lifetime

- **6782, RE:** full-width layers share a percent-clip cursor, in order: lagging, deferred, healing, `bullet_shield` (barrier), `ratking_armor`, delta. The displayed total is `max(max HP, HP + barrier + delta)`; the `client.dll` line builder at RVA **`0x1bf1590`** deletes surplus `UnitHealthbarLines` children as that total drops. ### Parser limits and API tables (6861 DLLs, disassembly, 2026-11-13)

Full evidence: [research/dll-tooling-findings.md](research/dll-tooling-findings.md). Machine-readable copy: `tools/lib/engine-facts.json`, enforced by `tools/lib/stylesheets.js`, `tools/engine-facts.js --check` and the strict test adapter. Not checked in game.

- A rule's selector list is read into a 2,048-byte buffer: at most 2,047 bytes, comments and whitespace included ("Failed to parse selector"). One selector is at most 256 characters ("Selector exceeds temp buffer size"). No selector-count limit exists; 10 selectors / 1,024 characters is this lane's own ceiling.
- A property name or value is at most 4,095 bytes; `@define`, `@keyframes` name, keyframe selector and `@import` text at most 1,023 bytes.
- 140 CSS properties are registered. An unknown property is a parsing warning that drops the declaration. Only `@define`, `@keyframes` and `@import` are supported; another at-rule or a selector failure is a parsing error that probably fails the sheet. Combinators are space and `>`; `+` and `~` are rejected. Unknown pseudo-classes: behaviour not determined.
- The JS API has 28 `$` functions and 1,121 events with declared argument counts. Scripts cannot read dialog variables. `GameUI` members are not in the DLL strings; where they are defined is not determined.
- World health bar: the client sets only `health`, `name` and `player_level`; `health_total_lg/md/sm` come from stock `@define` thresholds 4000 and 2000. Nothing exposes max HP or barrier to CSS or JS.

## Kill bounty (ticket 50)

- **Static RE, 6839 (2026-11-02), not live:** the client exposes no per-player kill bounty. The only bounty dialog variable is `neutral_bounty` (neutral camps); `m_iComebackBounty` is Golden Idol / KOTH VData. `server.dll` (SHA-256 `e7db4fca…`) computes a hero kill as `S + bonus + comeback(S)`: base `B = (int) remap(game seconds, 0..2400 → 200..2200)` (the victim's net worth is only logged), solo `S = ceil(B × 1.25)`, comeback multipliers 2.268 (team, lead above 1,500) and 2.484 (victim above the killer team's average, which must exceed 1,250), cap 5 or 7 from minute 8, +0.15 unless capped or the winning-team case, extra `(int)(((int)(S × mult) − S) × 0.4)`. New since 6753: 70 % of each comeback share goes to the same team's two lowest net-worth players, so the team total is unchanged. Source: `.scratch/bounty_re/EVIDENCE.md` (decompiles), [ticket 50](issues/50-kill-bounty.md); constants match the live-checked `feeder_feed/design.md`.
- **Topbar inputs (6839 stock `citadel_hud_top_bar_player.xml`, decoded with Source2Viewer):** each card has `#SoulsValue` (`{s:gold}`) and sits under one of the two `CitadelHudTopBarTeam` panels; the clock is `#GameTime`. The runtime pairs each card with the other team panel, so it does not depend on which side the local player is on.

- **Live 6839 (2026-11-02, hero testing, `-condebug` console.log):** the server logs every hero kill as `GameTime: …, Base Bounty: B, Total Bounty: B(+125)`, `Comeback Active - … Bounty Base: S, Total Comeback: N, Killer Portion: K, … TotalVictimTeamNW, TotalKillerTeamNW` and `Comeback paid hero_<killer> K`. The kill popup is `S + 125 (the killer's own first kill) + K` with `K = int(0.3 × N)`; the rest of `N` goes to assisters and teammates. Six kills over two sessions matched (1,483 / 1,396 / 1,417 and 835 / 732 / 759). Static RE adds that `K` loses `int(0.7 × K)` to tick gold when the killer's net worth is above the victim team's average.
- **Live 6839 topbar timing:** `#GameTime` trails server time by about 1 s (kills at labels 3:40 / 3:55 / 4:11 paid the base of 3:41 / 3:56 / 4:12). The `FriendlyKills` label (`{i:friendly_kills}`) read 0 for 22 s after the first kill, while the victim card's `Dead` class appears at once. `TeamScoreFriendly`/`TeamScoreEnemy` (`{s:team_networth}`) match the server's net worth to their rounding ("50k" for 50,400); a card's `{s:gold}` can read above it (local card 2.1k at server 1,515).

  - Panorama: stock `.WindowRoot` is `width/height: 100%`, the overlay `<root>` has no size attribute, and `overflow: noclip` only reaches the canvas bounds. Scaling content down and back up ends at the same pixels. **Live 6861 (self-test, test pak `fa12813a`):** `height: 260px; margin-top: -50px; overflow: noclip` on `.WindowRoot` moved the name and bar 50 px up, and the status row, now above the canvas top, was not drawn.   - Drawing from the HUD context instead: no `WorldToScreen`, `Entities` or `Game` API string in Deadlock's client, panorama or panoramauiclient DLLs, and the HUD context has no handle on world panels (contexts only exchange `ClientUI_FireOutput` messages). Not probed live.
  - Room that exists: stock content ends near y 93-105 of 210, so about half the canvas below the bar is unused. Content can be shifted down inside the canvas (name `margin-top: 45px`, `#UnitStatus` `margin-top: 65px`, row y 0-32) to make room for a taller status row; the bar then sits lower over the hero.
- **How the canvas height is computed per hero (static RE client.dll 6839 `a6310c2e`, 2026-11-02; prompted by yesdaddy's live test where Rat King did not move):** each hero model carries `CitadelUnitStatusSettings_t` (`m_strUnitStatusAttachmentName`, `m_vUnitStatusOffset`). The per-frame update `sub_181E8D6E0` computes, only when the model names an attachment, `z = max(citadel_unit_status_offset_player_min_z (75), healthbar_attachment_z + citadel_unit_status_offset_player_z_offset_adjustment (16))`, smoothed with an exp lerp, then adds `m_vUnitStatusOffset`. So the setting is ADDED to each hero's own (animated) attachment height: it keeps the per-hero differences and moves every attachment hero by the same amount, except heroes pushed up to the 75 floor, which move less. A model with no attachment never reads either setting; its canvas sits at the fixed `m_vUnitStatusOffset` z. Model survey (`.scratch/zoff_vdata/survey.py`, `all/survey.json`): every playable hero uses the `healthbar` attachment except **Rat King** (no attachment, fixed z 128) and the target dummy / generic person (fixed 95). That is exactly why Rat King's bar did not move in the live test while Infernus's did.
- Convar options from that formula (inferred, not live-tested): no convar reaches the no-attachment branch, so nothing moves Rat King or the target dummy. Uniform shift: raise `_z_offset_adjustment` (Rat King stays). Same height for every hero: set `_min_z` to H and `_z_offset_adjustment` very negative (e.g. -500; the dump lists no min/max for it) so every attachment hero is clamped to H; H 128 matches Rat King's fixed 128. Cost: the bar stops following the attachment (crouch, slide, animation), as Rat King's already does. Both are developer-only, so `gameinfo.gi` only.
- Per-hero attachment heights (2026-11-02, `.scratch/zoff_vdata/heads.py` -> `heads.json`; bind pose from each model's skeleton, model scale and animation not applied, so rough): every playable `healthbar` attachment sits on the head bone with zero offset (Infernus `head`, Mo & Krill `rider_head`, baba `baba_head`). Bind-pose z ranges from 41.6 (Mo & Krill, Rem; both floored to 75 in stock) through 89.5 (Infernus) to 106.2 (Abrams). So `_z_offset_adjustment` is per-hero aware: it puts every bar the same distance above its own head. yesdaddy's 128 test adds 112 over stock (more than Infernus's head height), so every bar floats far above; compare a short hero (Paige 73.8, Grey Talon 75.3) with Abrams at a small value (24-40) instead. - **Status-effect cap (static RE, client.dll 6839 `a6310c2e`, 2026-11-02; not live-verified):** `CCitadelStatusEffect` shows at most **4** modifier panels. Its constructor (0x181E46400) sets the limit field (+176) to 4; the update (0x181E5B2C0) first adds one panel per shown modifier state (stuns and other state-driven panels, uncounted), then walks the remaining modifiers and stops at `count >= limit`, so pickups and debuffs past the fourth never get a panel. The limit is the panel attribute `max_modifiers` (vt[26] 0x181E43840 parses it with `V_atoi`; its sibling attribute `display_location` takes `healthbar` / `bottom_left`), so a layout could set `<CitadelStatusEffect id="StatusEffects" max_modifiers="6" />`. Not changed: user decision 2026-11-02 to keep the game's status row as it is. The 200 px canvas fits about six 30 px icons in one row. Artifacts: `.scratch/status_cap_re/out2/` (decompiles, `report.json`), `pass4.txt` (attribute name).

## VM audit mechanisms (2026-10-16)

These are implementation constraints and synthetic evidence, not new native-engine findings:

- Preview ancestry is memoized only within one paint. Renderer validity and per-axis UI scale are shared only within one measurement; neither may survive into the next sample.
- Unrelated menu publications skip own-HUD resolution. The independent one-second watch still checks the complete ancestry, including the HUD root's link.
- Topbar structure/configuration reconciliation is separate from ring progress. Artwork recreation clears its style/structure caches. Retirement and stop share a same-context card-lease registry; independent cleanup retries failed parent/order/alignment restoration even while both timers are disabled, and blocks overlapping ownership across reincarnations.
- Generated layouts load only their timer role: world sampling at three seconds (optional one-second ultimate prediction), HUD discovery at five seconds and moving-ring/ultimate updates at one second. Wire messages, publisher epochs and replay rejection are unchanged.
- The shared adapter counts explicit validity/query boundaries separately from recursive mock traversal, and records schedules and child-order calls. Historical 300/200/30 and HUD-watch ceilings are unchanged; supplemental counts must not be added to the old metric or presented as FPS.
- Renderer timing clocks and accumulation use the same debug markers as timing logs. Release stripping removes all of that accounting; staged debug tests still observe timing summaries.

Retained before/after observations and limits: [audit results](../.scratch/hpv3_audit/RESULTS.md). Native CSS loading, packages and frame time were not checked by this audit.
