### 1. Settings / Bundle COPY — reproduced live; fixed in source, live re-check pending

- **Frames checked:** `c15_presets.mkv` at **22 s** shows Presets with empty code boxes and no error; **23 s** is back on BAR. Its action log has no click on Bundle COPY. In `hp_colors_v3_full_take_1080p24.mp4`, **34 s** shows the preset toolbar, **36 s** and **38 s** show the HEROES dialog, and **40 s** is BAR. None shows a failed Bundle COPY. `backup_bundle_code.txt` does contain `full_take`, but stale clipboard contents alone do not establish that COPY was attempted.
- **Live evidence supplied by Main (2026-10-17, Deadlock 6785 debug):** Bundle COPY reports “That code could not be read.” Debug output is `[HPV3] code Bundle copy failed: Invalid number of arguments for event in DispatchEvent for CopyStringToClipboard stack=`. Settings COPY fills its entry but throws the same value instead of reporting copied. The thrown value is not an Error and has no `.message`.
- **Cause:** [`codeAction`](../panorama/scripts/hp_colors_v3_menu.js) dispatched `CopyStringToClipboard` without a clipboard-local catch or checking `false`. The client's argument rejection reached the outer import/export catch, whose fallback incorrectly described a reading failure. This is independent of valid export-size or record-validation refusals.
- **Fix:** isolate the direct clipboard route; on throw or `false`, focus the visible code TextEntry, select all and dispatch `TextEntryCopyToClipboard`, matching the released v2 fallback. Leave the code visible. Report `<noun> copied.` only on accepted dispatch; if both routes fail, show neutral “Code is in the box; copy it manually.” Debug-only logs name the successful route; the existing outer catch log remains.
- **Red-green regressions:** eight Settings/Bundle cases in [`menu-actions.test.js`](../tests/menu-actions.test.js) failed before the runtime fix and pass afterward: direct dispatch throws the exact live non-Error string or returns `false`; fallback succeeds with the correct entry, focus, selection and code; fallback throwing or returning `false` produces neutral manual-copy guidance and no clipboard write. The [adapter](../../scripts/hp-colors-panorama-test-adapter.js) models both clipboard routes. Existing real-storage round-trip and oversized-bundle tests retain export-validation coverage.
- **Main live re-check:** open Presets and click each COPY glyph beside **SETTINGS CODE** and **PRESET / BUNDLE CODE** (not the selected-preset toolbar COPY). Expect copied status and paste a matching `HPC3` code into a local editor. Repeat after applying the built-in default, applying a user preset and assigning a hero on normal and QOLLOCK. Confirm the debug log names `TextEntryCopyToClipboard`; keep any genuine export-size refusal intact. No live re-check is claimed here.

### 2. Slider Undo — reproduced live; fixed in source, live re-check pending

- **Recording review:** `c16_undo_reset.mkv` at **4 s** has Show healthbar disabled; **6 s**, after the sole Undo click at 5.56 s, has it enabled again. Hue drags occur at 8.70–10.00 s and 11.68–12.98 s; **14 s** shows the resulting colors, without an Undo. `c06_size.mkv` at **7 s** shows the completed width drag (230.12 px), without an Undo. These clips alone did not reproduce the report.
- **Live evidence supplied by Main (2026-10-17, Deadlock 6785 debug):** dragging **Low health threshold 25→64**, releasing and clicking **UNDO once** restored **62**, not 25. Temporary `console.log` probes recorded zero Slider `onmousedown`/`onmouseup` panel callbacks across clicks and drags. Native `$.RegisterEventHandler("SliderValueChanged", slider, fn)` fired every step, including menu sync; `SliderReleased(panel, value)` fired once at mouse release (`SliderReleased lowThreshold args=[panel,"64"]`). The `SliderFocusChanged` name exists in `panoramauiclient.dll`; its useful delivery semantics and keyboard release behavior have not been established.
- **Cause:** [`bindControl`](../panorama/scripts/hp_colors_v3_menu.js) started numeric and hue gestures only from mouse-down panel handlers that the engine never delivered. Every value change therefore made a separate Undo record and bypassed gesture publication throttling. Earlier tests directly called those nonexistent-in-practice mouse callbacks, hiding the defect.
- **Fix:** shared `bindSliderGesture` starts a gesture immediately before the first non-syncing user value change for that row. Native `SliderReleased` completes it; registration is guarded by the existing `bound` map **per panel instance**, and stale/replaced-panel releases are ignored. Numeric and hue sliders use the same path. Dead mouse-down/up bindings and all temporary probes are removed. Existing blur, other-row edit, page/side change and close paths still complete pending edits. No timing-based history heuristic was added.
- **Red-green regression:** `ticket 29: native numeric and hue drags each undo once after SliderReleased or release-outside blur` in [`menu-actions.test.js`](../tests/menu-actions.test.js) failed on the original runtime with **actual lowThreshold 62, expected 25**, then passed after the fix. The [VM fixture](../tests/boot-layout.js) now swallows Slider mouse panel events, emits `SliderValueChanged` plus `onvaluechanged` on value writes (including sync), and dispatches native `SliderReleased` with panel/value arguments. Coverage retains no-op drags, page/close completion, hydration and hero-route deferral; numeric and hue 1 kHz gestures publish at most once per 50 ms, publish the final value immediately, save once and Undo to the opening value. The late-panel retry test checks exactly one native release registration for both slider types.
- **Keyboard behavior / remaining unknown:** keyboard value changes use the same lazy session. Without a native release they finish on blur, navigation, close, Undo or another row's edit. Regressions verify that blur separates a keyboard edit from a later same-row drag, and a different-row drag cannot absorb the edit or be ended by the earlier row's delayed release. Whether native keyboard steps emit `SliderReleased`, and whether switching from keyboard to mouse on the **same still-focused slider without blur/release** supplies any distinguishable boundary, remain unverified; do not claim per-keystroke Undo or a separate session without such a boundary.
- **Preview audit:** [`hp_colors_v3_preview.js`](../panorama/scripts/hp_colors_v3_preview.js) uses only `onvaluechanged` for Health input (`onSlider`); it has no mouse-down/up reliance and needs no change for this defect. Its separate track-click report remains open below.
- **Main live re-check:** freshly open the menu. Repeat Low health threshold **25→64**, release, then Undo **once**: expect **25** and disabled Undo. Repeat hue, a track click followed by a drag, consecutive drags, release outside, and blur/page/close completion on normal and QOLLOCK. Try keyboard steps followed by blur and a new drag; also record the native events when moving from keyboard to a drag without changing focus. Confirm no script errors and no temporary probe output.

### 3. Search scroll offset — fixed in source, live verification pending

- **Observed fault:** `c13_search.mkv` at **4 s** and **6 s**, after entering `outline` at 3.51 s and before the first wheel event at 6.50 s, starts mid-results: the BAR/page and OUTLINE/card headers are scrolled away above the first visible rows. At **17 s**, after deleting the search, BAR retains a partial-row offset instead of returning to its header.
- **Cause:** [`applySearch`](../panorama/scripts/hp_colors_v3_menu.js) fitted the first matching **row**, not the results header, immediately after changing visibility across pages, folds and columns. Clearing search did not reset the list offset. Exact native relayout/event timing is not recorded; stale geometry is an inference, while the row target and missing reset are directly observable in source.
- **Fix:** use the settings list's native `ScrollToTop()` after filtering or clearing search. Remove the geometry-dependent first-row fit; retain the landed-card title highlight. No CSS, custom coordinate calculation or scheduled scrolling was added.
- **Red-green regression:** `ticket 29: search starts at the results header and clearing it resets the page offset` in [`menu.test.js`](../tests/menu.test.js). A pre-fix direct-shell run failed with **240 !== 0**; after the fix it checks results/header origin, no first-row fit, and clearing a scrolled result list. The fixture models the observable scroll API effect, not native layout.
- **Main live check:** scroll down, type `outline`, and confirm BAR plus the first matching card header remain visible at the top. Wheel down, clear the query and confirm the normal page starts at its header. Repeat rapid query edits, no matches, and a subnavigation jump after search, on normal and QOLLOCK variants.

## User report: code import, stamina paint, endless wobble (2026-10-17)

- **Import refused by box.** A settings code pasted into PRESET / BUNDLE CODE failed with "Use the matching settings or bundle paste box for this code." Cause: each box decoded only its own kind. Fix: [`decodeCode`](../panorama/scripts/hp_colors_v3_menu.js) tries the box's kind, then the other kind. IMPORT now follows the code: a settings code applies (an Undo-able, saved edit) and a bundle only appends presets. REPLACE ALL with a settings code says to use IMPORT. When both decoders fail, the error comes from the decoder that recognised the kind. Both boxes accept 32,768 characters; their help text says what IMPORT does. Tests: `storage.test.js` "a settings code pasted into the bundle box …" uses the user's exact code and covers apply, unchanged presets, Undo, a corrupted checksum, save and restart. "corrupt imported codes … a bundle in the settings box only adds presets" covers the reverse direction. The first test failed when the fallback was removed.
- **Preview unavailable after import (found live).** The user's code enables enemy stamina color. With the custom-color arrow shape, the renderer wrote `wash-color: offBlack` inline on empty pips, and the game rejected it: `Invalid value for property 'wash-color': offBlack`. Every preview paint then threw ("Preview unavailable"), and enemy world bars with visible empty pips hit the same write. Fix: write `#10130D`, the value the owned CSS already uses for `offBlack`. The [style guard](../tests/boot-layout.js) now rejects colour macros in inline colour writes, which failed the two existing stamina tests before the fix. New test: "user code with stamina color on paints the preview on every page and side", which failed when the fix was reverted.
- **Codes copied from chat failed to import (2026-10-17).** Codes pasted with a label (`code:`), Discord backticks or a code block, quotes, a trailing period or comma, a line break or a zero-width character were refused as damaged. HPCR2 (v2 settings) codes were also misrouted: their 5-character tag was mistaken for `HPC3.` and sent down the v3 path. Fix: [`pastedCode`](../panorama/scripts/hp_colors_v3_codec.js) keeps only the first code. For HPC3 it drops whitespace and stops at the base64url payload. For HPCR2/HPCRP1 it removes raw line breaks and tabs, which JSON never contains inside strings, and stops when the JSON value closes. A v2 tag picks its decoder first (`decodeCode`). The HPC3 checksum and v2 JSON parsing still refuse real damage. Tests: three `storage.test.js` cases ("… code wrapped by chat imports from either box; a damaged one is refused") cover HPC3 settings, HPCR2 settings and HPCRP1 bundles, in seven wrappings in both boxes, plus a damaged copy. All three failed with the extraction removed. `codec.test.js` now corrupts inside the payload, since trailing junk is treated as wrapping.
- **Import/paint fuzz coverage.** `tests/import-fuzz.test.js` imports schema extremes and the user's code through the real menu path, paints the preview and enemy/ally world bars, rejects invalid inline styles and checks codec round-trips. It found no new fault. With the `offBlack` fix reverted it fails and names `washColor="offBlack"` at `hp_colors_v3_renderer.js:969`.
- **Endless wobble: not reproduced.** Live 6793 debug build `28388bb1`: toggling shake, changing strength to 8 and 6 on the slider, PLAY, editing and then hiding the Escape menu, and reopening all left the preview bar still within about 3.3 s (PLAY within 4.6 s). Pixel diffs of the editor column and the title stayed at 0, and the ally bot's world bar stayed level. The source and the release build schedule `previewShakeEnd` with a generation guard, and close/retire cancel it. The user observed the whole menu or the hero model moving after an unknown trigger; this needs a recording or exact steps.
