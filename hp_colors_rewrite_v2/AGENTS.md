# HP Colors Rewrite v2

## Scope

`hp_colors_rewrite_v2/` owns the ESC editor, its durable local save, and the live v2 unit-status renderer. Keep its whole-bar geometry and `HP_COLORS_V2_CONFIG` transport. Read `FEATURES.md` for feature behavior and manual smoke scenarios; use source and the build wrapper for current implementation details.

Settings, scopes, presets, and conditions persist on this PC through `hp_colors_v2_storage.js`. Do not add Anita compatibility, Reset All, or legacy v99 support. Preserve legacy HPCR2 imports and HPCRP1 preset compatibility; current exports include the `hpv2` v:2 extension for V2 settings and bar-relative HP-text offsets. The web preset builder still accepts only hpv2 v:1 and fewer extension slots: current exports are not compatible with it. ShowRank Barebones support is opt-in build-stage Escape composition; keep canonical runtime code independent.

Package ownership: the Rewrite v2 runtime is pak02 and the generic preset builder is pak96. v2 no longer reads a builder pak01 seed; an installed old pak01 overrides the ESC layout, and the menu reports it as `OLD PRESET VPK`. That legacy layout has four original rail buttons and explicit legacy navigation; it boots without the canonical selector, Advanced, Units, Presets, Names & Labels, and Own HUD controls until pak01 is removed.

## Durable save

- A hidden `CitadelHTMLPanel#HPColorsV2Store` loads `https://hantu-raya.github.io/hpv2-store/` once; its origin-local localStorage lives in Steam's CEF profile, not on the server. Each request uses `#` + `encodeURIComponent(JSON.stringify(request))` with a unique id; fragment changes trigger `hashchange` without reloading and are never sent to the server. Replies remain `HTMLTitle` titles prefixed `HPV2S1:`.
- Deadlock's 2026-10-01 update restricts `CitadelHTMLPanel.SetURL` to case-insensitive `https://` URLs; other schemes become `about:blank`. There is no script-execution method; `HTMLTitle` and `HTMLURLChanged` still work. Do not restore the removed file-page/script-injection bridge or production probe.
- Keys are data, not configuration: touch only `hantu.hpcolors.v2/state` and `hantu.hpcolors.v2/state.prev`. Third Eye and QOLLOCK no longer share this origin. Pre-update `file://` saves are unreachable from HTTPS; the first launch on the new origin starts without a save.
- Records are `HPV2S1.<fnv1a32>.<base64url envelope>`; current envelope schema 4 embeds the body and maps to bar-relative offset version 2. Schemas 1–3 still load (schema 1 has a string body; 1–3 map to absolute offsets). Schema 5 came only from a withdrawn centered-HP-text test build; it is read as schema 4 without conversion and never written. See `design.md` for migration. The envelope, not a body marker, owns the durable offset version. Classify absent/valid/corrupt/unsupported, including body shape, before normalizing. A corrupt or absent current falls back to `prev`; a newer-schema current never does. A commit rotates the current record into `prev` only when its checksum matches the record this bridge validated or wrote.
- Accept readiness only for the latest hello id, exact hosted HTTPS page address, and page protocol version 1; missing or mismatched versions fail closed. Re-send hello every 8 s until a trusted page event proves navigation reached the surface; readiness is bounded at 30 s. An offline or incompatible page leaves saving unavailable. A lost reply fails its request after 5 s; a timed-out read is asked once more under a fresh id, and the editor's save retry below is the only other retry.
- The hosted page source is `D:/hpv2-store/index.html` in `Hantu-Raya/hpv2-store`. GitHub Pages serves it with `max-age=600`, so updates can take up to 10 minutes to reach a client. Any protocol change must bump the page/bridge version and remain backward-aware; never bypass the version gate to accommodate cached pages.
- Live HTTPS probe logs `.scratch/hpv2_probe/launch1_console.log` and `launch2_console.log` proved 30 KB request URLs, one page load, and localStorage persistence across restart. The probe was removed in 058d51e; the production HTTPS transport landed in 621c7ad.
- Writes stay closed until a read in this process proves what the store holds. Failed, corrupt, or future-schema reads block saving for the process instead of overwriting with defaults.
- The saved body is `sessionRaw` without `effectiveRevision` and with only values differing from the frozen 974128a sparse baseline, not the new shipped defaults. Preserve that baseline for saves, codes, presets, and missing-stamina-shape derivation so old data keeps its look. Saves throttle at 1.5 s, flush on editor close, skip unchanged bodies, retry failures with backoff (status SAVE RETRYING, then SAVE UNAVAILABLE), and keep one active plus one replaceable pending write. After Forget, only a deliberate edit (not `AUTOMATIC_INTENTS`) creates a save again.
- Root attrs `hp_colors_v2_store_status`, `hp_colors_v2_store_ack`, and `hp_colors_v2_hydration` carry process evidence across ESC layout reloads. Renderers keep bars stock while hydration is `pending`.

### Changing the hosted page

The page is part of the save contract but ships outside pak02. `scripts/validate-hp-colors-rewrite-v2-storage.test.js` (and so the build wrapper) runs the local `D:/hpv2-store/index.html`, not the live page, so green tests do not prove what players load.

1. Edit only `D:/hpv2-store/index.html` and keep its `README.md` (protocol table, snippets, limits) in step.
2. A request/reply format change bumps `VERSION` in the page and `PAGE_VERSION` in `hp_colors_v2_storage.js` together; the old mod must fail closed against the new page and vice versa.
3. Run the storage suite, then commit and push `Hantu-Raya/hpv2-store`.
4. Before deploying pak02, confirm the live page matches: `curl -s https://hantu-raya.github.io/hpv2-store/ | diff --strip-trailing-cr - D:/hpv2-store/index.html` prints nothing, and `gh api repos/Hantu-Raya/hpv2-store/pages/builds/latest --jq .status` is `built`.
5. Then build, deploy, fully restart, and check `[store] bridge ready at https://…` in `console.log`. Allow 10 minutes of Pages caching before calling a mismatch a bug.

Never ship a pak02 that expects a page version that is not live yet. Pushing to that repo publishes immediately; it needs the user's go-ahead like any release.

### When saving is unavailable

Read the `[store]` lines in `game/citadel/console.log` before changing timing or retries. On 2026-10-01 two timing fixes (cbf38d9, 790775c) chased a missing page when the real cause was the new `https://` gate.

- Only `page event about:blank` after each request means the panel rejected the address. Check the `SetURL` gate in the current `citadel/bin/win64/client.dll` (find the `"https://"`/`"about:blank"` references or decompile with IDA) before touching mod code.
- `ready_timeout` with no page event at all, or `protocol_version`, points at the network, the Pages deploy, or a version mismatch.
- Suspect a game update before a recent mod change: compare `steamapps/appmanifest_1422450.acf` `LastUpdated` and `client.dll` mtime with when saving last worked. An A/B build of the previous mod commit settles it in one launch (the HUD wash change was wrongly suspected that way).
- Steam client updates are separate (`d:/steam/logs/bootstrap_log.txt`); its CEF policy did not change on 2026-10-01.
- The QOLLOCK compatibility lane pins the QOLLOCK 4.0.3 1 October hotfix `pak03_dir.vpk` (SHA-256 `27e9bb93…`) from `qollock403_1octoberhotfix.zip`. It conflicts with any other pak03, including this repo's abilities pak03. Preserve every pinned Escape-menu include/panel, especially persistence scripts and `#QOLStorageBridge`; QOLLOCK owns `hud.xml`, while the wrapper composes its topbar with HPv2 pickup-timer includes. See `FEATURES.md` for refresh/install rules.
- The 1 October hotfix replaces only QOLLOCK's `core/ql_storage_bridge`, `hud.xml`, topbar-player layout and topbar CSS; its Escape menu and topbar layout are unchanged from the 30 September 4.0.3 pin. Its storage bridge no longer issues `javascript:` requests (blocked by the 2026-10-01 gate), so QOLLOCK saving should work again; confirm in game. HPv2 saving is independent; the bridge page and keys are separate. Do not copy QOLLOCK storage code into the compatibility package.

## Initialization

- `hud_escape_menu.xml` calls `$.HPColorsMenuBoot()` on load. Resolve required panels, hydrate, restore state, create dynamic controls, then bind events. Publish, start the config-request listener and identity watches only after setup succeeds.
- Cold boot reads the store before creating state; the menu button shows `Loading` until then. Warm boot uses the session attribute and skips the read when process evidence exists.
- Boot is idempotent after success. Failed control creation leaves boot retryable through another explicit call; there is no automatic retry loop. Preserve both missing-panel and thrown-API recovery.
- Hydrate through the state factory with `{sessionRaw, publishedRaw}`. Preserve the published effective snapshot while hero identity settles.
- The renderer registers its config event handler before `scan()`. The first scan reads the root snapshot and discovers live panels, then `paintColors()` starts. Keep one scan loop and one paint loop per context.
- Exercise startup changes in the editor VM validator, including failed setup, successful retry, and repeated boot without duplicate publication or scheduled work.

## Runtime rules

- Persist only through the storage module and only while the write gate is open.
- Preserve the v2 message magic, root attribute, payload version, and `{magic_word,version,revision,values}` shape.
- Publish every effective change immediately; no periodic replay. A unit-status context without config sends a small `HPV2_CONFIG_REQUEST` through its sibling relay (never `ClientUI_FireOutput` from the `ClientUIDialogPanel` itself) with 0.5/1/2/4/8 s backoff, then every 8 s, stopping on config, teardown or root change; three consecutive relay failures end it. The Escape menu keeps one request listener (replaced on layout reload) and answers with the current published payload at most once per 0.5 s window (one trailing answer per burst), including while the master switch is off, never while hydration is pending. Broadcasts and answers carry only keys that differ from shipped defaults; the root attribute stays full.
- Each unit-status context has one `ClientUI_FireOutput` listener, owned by the renderer: it routes by substring (config → renderer; `HPV2_PICKUP_*`/`HPV2_ULTIMATE_SNAPSHOT` → `context.HPV2OnPickupMessage` registered by `test_topbar_pickups.js`) and never parses other messages. Only the topbar HUD context registers its own listener. Ultimate snapshots carry [name, angle, rounded degrees/second], sent on player-state changes, a ≥15° prediction miss, or an 8 s heartbeat; receivers extrapolate smoothly, stay below 360 until ready is observed, and expire after 12 s. Hero bars re-send pickups only on mask/name change, refresh, pause, a missed prediction or the 6 s heartbeat.
- Classify unit kind separately from relation. Neutral-first precedence remains; only known neutral NPCs get the explicit fixed-fill opt-in. Enabled NPC, neutral, and building UNITS gates also apply shared bar size/position, native HP text, and contained health lines; gate off restores stock. OBJECTIVES retains internal building keys; class mapping is in `design.md`. Enemy and neutral HP text uses ENEMY settings, friendly HP text uses ALLY settings, including font, size, colors, offsets, and outline. Kill marker, pulse, level, ultimate, and stamina customization stays player-only. Unknown type/relation and conflicting enemy/friend ownership stay stock.
- Lane troopers are engine-drawn (not Panorama) and intentionally not customizable; the game's own Custom UI Colors setting is the only way to recolor them.
- Bar width and height accept 60–400%.
- The QOLLOCK pak02 ships its own Escape-menu copy (`hp_colors_rewrite_v2_qollock/panorama/layout/hud_escape_menu.xml`). After adding or renaming any HP Colors menu element, rebuild it with `build_hp_colors_rewrite_v2_qollock.ps1 -RefreshFromInstalledQollock -QollockPak <pinned path from qollock-source.sha256>`; the build fails while any canonical `HPColors*` id is missing, and an editor test boots that copy.
- `#name` sits in `HPV2NameAnchor` inside the full-canvas `HPV2MotionFrame`, so it shakes with the bar. Damage wiggle/transition animates that one frame (name anchor, `UnitStatus`, `hp_counter_container`); keep it full-canvas, since a transformed compact frame clips its noclip children in game, and stays off for buildings and bosses. Never animate `#name` itself: the renderer owns its inline transform.
- Damage shake (slots 76 `damageShakeEnabled`, 77 `damageShakeIntensity` 1-10 deg, defaults true/3) is gated root classes only: `HPColorsRewriteShakeOff` or one `HPColorsRewriteShake<N>` (none at 3) swap `animation-name`; those rules stay before the boss/building `animation-name: none` rule so objectives never shake.

### Release checklist (lessons from 2.2.0)

- **Every variant ships, not just the one you deploy.** The game here runs the normal pak02, so live checks never exercise the QOLLOCK pak02. Before handing out archives, rebuild both: `build_hp_colors_rewrite_v2.ps1` (deploys) and `build_hp_colors_rewrite_v2_qollock.ps1 -SkipDeploy` (root `pak02_dir.vpk` becomes the QOLLOCK build; never deploy it here).
- **Menu rows change → refresh the QOLLOCK menu copy.** Any added or renamed `HPColors*` element in `panorama/layout/hud_escape_menu.xml` must reach `hp_colors_rewrite_v2_qollock/panorama/layout/hud_escape_menu.xml` via `-RefreshFromInstalledQollock -QollockPak <path in hp_colors_rewrite_v2_qollock/qollock-source.sha256>`. A stale copy made 2.2.0 QOLLOCK boot with a greyed-out HP COLORS V2 button and default settings. The build guard and the editor test "the shipped QOLLOCK Escape menu boots the editor and publishes settings" now catch it; never weaken either to get a green build.
- **Do not trust the installed pak03.** On this PC `citadel/addons/pak03_dir.vpk` is an unrelated 377 KB addon, not QOLLOCK. Always refresh from the pinned 4.0.3 file named in `qollock-source.sha256`.
- **Archives and changelogs follow every shipped change.** After any change that alters a built pak02, repack both `hp_colors_rewrite_v2_<ver>.7z` and `hp_colors_rewrite_qollock_v2_<ver>.7z` (single member `pak02_dir.vpk`; extract and compare its SHA-256 to the build), and add the player-visible line to `docs/changelogs/<date>_hp_colors_v2_<ver>.txt` and `_discord.md` in the same turn. Bugs fixed before a release ever shipped get no changelog line.
- **New appended settings break older versions.** Any new slot whose shipped default differs from its frozen default is emitted in every code and save, so older versions reject them; say so in the changelog Adjustment line.

Production scripts carry no debug logging; the renderer has no `$.Msg` at all. Keep validation against debug flags, profiling collectors, temporary probes, and root-budget attributes. For a one-off live trace, instrument a local build and do not commit it.
