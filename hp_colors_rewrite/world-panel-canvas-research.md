## Ancestry and geometry trace

1. `CUnitStatusOverlay` is a `C_PointClientUIWorldPanel`, whose entity-side resource identity is `m_DialogXMLName`/`m_PanelClassName`/`m_PanelID` and whose world-panel side owns `m_flWidth`/`m_flHeight`/`m_flDPI` plus render-to-texture flags (client schemas above).
2. The selected dialog resource builds `WindowRoot` → `UnitStatus` → `InfoHealthContainer` → `UnitHealthbarContainer` → `unit_healthbar_active_parent` → stock pip label (XML lines 41–64).
3. In the stock v1 vertical class, `WindowRoot` is transformed and sized `80%×100%`; `UnitStatus` is fit-to-children with `padding:300px`; `InfoHealthContainer` and `UnitHealthbarContainer` have finite/fit-to-children sizes (CSS lines 28–67, 76–95, 328–355).
4. `overflow:noclip` on `#UnitHealthbarContainer` does not remove the stock `#unit_healthbar_pip_label { overflow: clip; }` (CSS lines 336–354, 722–742). In vertical mode that stock pip label is collapsed, so a custom `hp_counter` must be analyzed separately.
5. The local custom counter is an ignored-flow child of a bottom-aligned `100%×100%` anchor; runtime writes `translate3d(x,y,0)` to the anchor, not the label (local `healthbar_probe.js` lines 704–709 and 815–826). The `399px` extent is in-flow and can change desired layout; the anchor transform alone cannot declare an entity render target.
6. The live screenshot narrows the immediate seam: the custom anchor is inside the 300px `InfoHealthContainer`, whose top is at local `y=649`. Moving the anchor to be an ignored-flow sibling of `InfoHealthContainer` under `UnitStatus` would change only this ownership seam while retaining the same `CUnitStatusOverlay` world-panel host.

## Diagnosis

### Proven source facts

- The overlay has a world-panel entity layer with independent networked width/height/DPI and render-target-related flags; the XML/CSS source only declares a Panorama child tree and style rules ([`C_PointClientUIWorldPanel.h`](https://github.com/SteamDatabase/GameTracking-Deadlock/blob/master/DumpSource2/schemas/client/C_PointClientUIWorldPanel.h), [`unit_status_overlay.xml`](https://github.com/SteamDatabase/GameTracking-Deadlock/blob/master/game/citadel/pak01_dir/panorama/layout/unit_status_overlay.xml)).
- Stock v1 deliberately uses transforms, fit-children sizing, `padding:300px`, and several `overflow:noclip` declarations. Stock v2 likewise uses `overflow:noclip` on `#UnitStatus`, `#InfoHealthContainer`, and `#UnitHealthbarContainer` ([`unit_status_v2.css`](https://github.com/SteamDatabase/GameTracking-Deadlock/blob/master/game/citadel/pak01_dir/panorama/styles/unit_status_v2.css#L31-L50), #L119-L126, #L354-L366).
- Therefore “`overflow:noclip` is present” does not identify which clip stage removed a glyph: there are ancestor layout bounds, a label-local `overflow:clip` in the stock path, and a world-panel render target.

### Strong inference (not an engine-source proof)

- **XML/CSS cannot directly enlarge the underlying world-panel texture.** No XML/CSS declaration in the tracked overlay maps to the entity fields `m_flWidth`, `m_flHeight`, `m_flDPI`, or `m_nExplicitImageLayout`. XML/CSS **can** enlarge a Panorama panel's desired/layout bounds (for example, the local in-flow `1px×399px` extent); if the engine auto-sizes a world panel from desired size, that could indirectly change the target, but that auto-sizing rule is not present in the tracked sources.
- The most likely explanation for a stable disappearance near `-300px` is a finite upstream layout/render surface, not the `overflow` setting on `UnitHealthbarContainer`: `padding:300px` is a stock v1 boundary and the local test specifically drives the custom anchor to `-300px`. This correlation is only a hypothesis until the experiments below are run.
- A custom-label-only raster bound remains plausible if a solid panel survives past the point where glyphs disappear. The stock pip label's explicit `overflow:clip` demonstrates that labels have an independent clip mode, but it is collapsed in vertical mode and therefore cannot by itself prove the custom-label failure.

### Unknown engine internals

- Whether `C_PointClientUIWorldPanel` allocates a fixed render texture from `m_flWidth`/`m_flHeight`, derives it from desired layout, or clamps it to a hidden maximum is not disclosed by the public GameTracking sources.
- The default/actual `m_flWidth`, `m_flHeight`, `m_flDPI`, and `m_nExplicitImageLayout` values for each live unit-status entity are not in the tracked XML/CSS or public map text. `client_strings.txt` proves typed spawner/resource symbols, not their runtime values.
- The exact order of world-panel render-target clipping, Panorama ancestor clipping, transform bounds, and label glyph/texture clipping is unknown. Do not infer it from browser CSS.
- The world-panel culling cvars are update/culling controls with `<no description>`; the tracked source does not establish that they enlarge or shrink the render target.
- Current convar inventories confirm client-side `citadel_unit_status_height` default `100` and `citadel_unit_status_width` default `200`; both are marked `developmentonly` and have no description. Current `popup_settings.xml` nests each `CitadelSettingsSlider convar="…"` inside `PopupSettingsSettingsRow`, but that custom row depends on the `SettingsRow` snippet owned by the popup-settings context. Instantiating it from `hud_escape_menu.xml` caused `FATAL ERROR: Unable to load snippet SettingsRow` during startup, so the controls were removed. A popup-settings row cannot be reused in the HUD editor, and it would not bypass development-only flags.

### Live height experiment

The transition-only geometry probe measured a `2000px × 1000px` `panorama_world_panel_*` root at readout offsets `800`, `840`, `900`, and `1000`. The owned counter remained laid out at `829px × 949px`, its window Y matched the requested offset, and the `UnitStatus` and context dimensions did not change. After the user ran `citadel_unit_status_height 200`, the same probe measured a `2000px × 2000px` root while the context remained `2000px × 949px`, `UnitStatus` remained `1290px × 949px`, and `InfoHealthContainer` remained at window Y `649px`. This proves the convar controls the engine world-panel canvas height in the tested `-dev -tools` session without changing the stock child layout. It does not prove that a retail session accepts the `developmentonly` command.

The ESC runtime could not issue the development-only command through `GameInterfaceAPI.ConsoleCommand`. The comparison in `test/custom_fov/panorama/layout/popups/popup_settings.xml` binds the likewise-development-only `r_aspectratio` through a native `CitadelSettingsSlider`, but live testing confirmed that this binding still requires prior `gameinfo.gi` exposure. The popup override and automatic `gameinfo.gi` patch were both rejected for the portable release. The VPK keeps the stock `1000px` engine canvas and constrains its vertical placement range accordingly.

## Development-only convar route audit

The relevant convar is registered by the client inventory but marked `developmentonly`: [`DumpSource2/convars.txt`](https://github.com/SteamDatabase/GameTracking-Deadlock/blob/master/DumpSource2/convars.txt#L4867-L4964) lists `citadel_unit_status_height` (default `100`) and `citadel_unit_status_width` (default `200`) with the `clientdll` and `developmentonly` flags. That is registration/flag metadata, not a Panorama layout setting. The live `-dev -tools` experiment changed the world-panel root from `2000×1000` to `2000×2000` only after the command was accepted; the ESC `GameInterfaceAPI.ConsoleCommand` attempt did not set it.

### Verdict

For the deployed addon to preserve stock healthbar geometry and work without an end-user editing `gameinfo.gi`, **no reliable VPK-only route is evidenced**. An installer can patch the installed root `gameinfo.gi`, but that violates the portable-addon requirement and is not used. A user-supplied launch option or cfg may set the value only after the startup registration/configuration gate is satisfied; neither is an addon-contained solution. The portable build therefore accepts the fixed engine canvas as a hard boundary and limits placement instead of pretending that XML/CSS or `overflow:noclip` can enlarge it.

## Ranked one-variable experiments

| Rank | Change exactly one thing | Diagnostic outcome |
|---|---|---|
| 1 | Move only `hp_counter_anchor` from inside `InfoHealthContainer` to an ignored-flow sibling directly under `UnitStatus`; retain its size, transform, label, and all root styles. | Cutoff moves/disappears ⇒ `InfoHealthContainer` ownership/layout is causal. Same cutoff ⇒ the limit is higher at `UnitStatus`/`WindowRoot`, the world-panel target, or label rasterization. This directly tests the seam exposed by the live debugger screenshot. |
| Rank 1 result | Moving the unchanged anchor from `InfoHealthContainer` to a direct `UnitStatus` child did not remove the live cutoff. The user measured about `-100px` at the maximum font size and `-20px` at the minimum font size. | `InfoHealthContainer` is not the sole limiting seam. The font-dependent threshold raises the probability of label/layout bounds, but does not yet exclude a desired-layout-derived or fixed engine target. |
| 2 | On one live `CUnitStatusOverlay`, raise only entity-side `m_flHeight` (or the map/entity key that feeds it); leave XML/CSS and anchor transform unchanged. | Cutoff moves with the field ⇒ engine render-target dimension. Cutoff unchanged ⇒ inspect layout/label stages; highest-value engine test because it targets the field XML/CSS cannot write. |
| 3 | Change only `hp_counter_top_extent` height `399px → 799px`; keep all styles and `translate3d(...,-300px,...)` unchanged. | Cutoff moves upward by the added desired extent ⇒ ancestor/auto-layout canvas. Cutoff fixed ⇒ fixed engine target or later clip. |
| Rank 3 result | Increasing only `hp_counter_top_extent` from `399px` to `799px` broke the live overlay. The experiment was reverted to `399px`. | A larger in-flow extent is not a viable fix. Do not repeat it; test the engine-owned unit-status dimensions or label-local bounds instead. |
| 4 | Change only `WindowRoot` height from `fit-children` to a large explicit height (for example `1200px`), with children/anchor unchanged. | Threshold moves ⇒ root/ancestor layout bound. No move ⇒ render target or label-local clip. |
| 5 | Replace only custom `Label#hp_counter` with a same-box solid `Panel` (same anchor, size, and transform). | Panel survives farther while text does not ⇒ label glyph/texture/local label clip. Panel disappears at same coordinate ⇒ ancestor/engine clip. |
| 6 | Keep the label but change only its box from `width/height:fit-children` to a large explicit box and retain `overflow:noclip`/`text-overflow:clip`. | Text boundary moves ⇒ label layout/raster bounds. No move ⇒ ancestor or engine target. Run after rank 5; do not change font, text, color, or transform simultaneously. |

## Valve documentation check

The first-party Valve pages consulted were [Panorama](https://developer.valvesoftware.com/wiki/Panorama) and [CSGO Panorama CSS Properties](https://developer.valvesoftware.com/wiki/CSGO_Panorama_CSS_Properties), including the `overflow`/`transform` property areas. Valve's site presented an Anubis anti-bot challenge in this environment, so those pages are listed as references but **not** used for decisive engine-behavior claims. The decisive evidence above is the current tracked Valve asset/schema/string source. Browser CSS behavior is intentionally not used.

## Bottom line

`overflow:noclip` is not a world-panel texture-size control. XML/CSS can enlarge child/ancestor layout bounds and may indirectly affect a target only if the engine derives target size from desired layout; the tracked source does not prove that derivation. To separate a fixed world-panel render target from a finite ancestor canvas and from label-local clipping, run ranks 1–4 in order, recording the first coordinate at which both a solid control panel and the text disappear.
