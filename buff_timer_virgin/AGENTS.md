# buff_timer_virgin — Agent Guide

## What the mod does

`buff_timer_virgin` ships as `pak98_dir.vpk`. It ships no `hud.xml`: its only stock override is `hud_minimap.xml`, which loads the timer and the settings script. Both scripts create their panels at runtime under stock HUD panels, so pak98 works next to mods that replace `hud.xml`. It only reads stock HUD panels and adds no network authority.

## Runtime architecture

- `boot()` takes `findRoot($.GetContextPanel())`, claims an instance generation and injects its hosts (see "HUD injection"). It caches stock panels (`Hud`, `TopBar`) from the root and its own panels from its own hosts, never by global id lookup, and binds `RejuvPingButton`/`BuffPingButton` with `SetPanelEvent` (no globals). It fills `SIDES[0|1]` with glow/claim panels, then calls `reset(1)` and `startGeneration()`. Missing core labels retry boot after 0.5 s. `resolveRejuvChargePanels` resolves `RejuvenatorFriendly`/`RejuvenatorEnemy` lazily, at most every 5 s. The first scan after rebinding only records `lastFound`, so an existing charge is not counted as a new claim.
- HUD injection (designed in a third Claude / GPT-6.1-Sol debate, 2026-10-08; widget layer moved 2026-10-09): `ensureTimerHosts()` creates four hosts with `$.CreatePanel`, three of them with `BLoadLayout("file://{resources}/layout/<file>.xml", false, false)`. None of these parents uses flow layout; z-index orders drawing.
  - `TimerOverlayFrame` (`bt_timer_overlay.xml`), the full-size widget layer, in `.clamp_width` after `#minimap_persp`. It holds six widget slots (`BTSlotBuff`, `BTSlotRejuv`, `BTSlotRift`, `BTSlotUrn`, `BTSlotClaimL`, `BTSlotClaimR`; each slot carries its widget, the pills their ping button, Rejuv also the mini card, the claim slots `MinimapBuffClaimLeft/Right`) and `BTEditLayer` with one unscaled edit chrome per slot (outline, `Handle{TL,TR,BL,BR}`, and `Side{L,R,T,B}` except on claim boxes). The claim boxes moved here from the former `ClaimOverlayRoot` host (2026-10-09).
  - `BTTimerDock`, an empty bottom-anchored 440 px box inside `#minimap_persp`: only the anchor for the default widget spots (the old `TimerOverlayFrame` box). A child of `#minimap_persp` placed outside its box is neither drawn nor clickable, even with `overflow: noclip` (probe 2026-10-09), so widgets cannot live there.
  - `MinimapGlowClip` (`bt_minimap_glow.xml`) and `BTLingerLayer` (`bt_linger_layer.xml`) in `HudMinimapContainer`, the minimap's parent.
  - Before creating a host, it deletes any direct child of the parent that has the same id. Valid owned hosts are reused, so a watchdog re-boot does not duplicate them. A failed `BLoadLayout` deletes the host and retries after 1 s; after 5 failures the instance retires. Missing parents retry indefinitely.
  - Generation guard: the first boot increments the int attribute `bt_timer_gen` on the HUD root. `timerAlive()` requires the context, the root and an unchanged attribute. `loop`, `watchdogTick`, boot retries, chat schedules and both ping handlers call `retire()` when it fails. `retire()` cancels every timer, chat, neutral, rotation and claim schedule, clears the lingers (restoring stock markers) and deletes its own hosts. It removes `bt-buff-timer` only while it still owns the generation (the layout give-up path). A superseded instance must never remove it: the successor writes that class once and caches the write, so it would not add it again.
  - The old `#HudMinimapContainer { overflow: noclip }` rule was dropped rather than inlined: stock `#minimap_container` already clips at 400px, and in zoomed mode stock's own `.useZoomedMinimap #HudMinimapContainer` clip rule won anyway.
- `startGeneration()` is the only way to start a loop. It bumps `_generation` and starts exactly one `loop(gen)` and one `watchdogTick(gen)`. `reset()` cancels the loop handle, the watchdog handle and any in-flight chat intent. The boot, hideout and backward-clock paths all use `reset(1)` followed by `startGeneration()`. The watchdog logs only through `dbgPing` and restarts boot when the loop misses its deadline by 15 s.
- `loop(gen)` is the only main schedule chain.
  - When the gate starts a run, it continues straight into the active lanes. The 30 s gate delay applies only while the run is still inactive, for example in the hideout.
  - During a match, each tick runs three lanes: `runMinimapLane` (shared snapshot), `runTimerLane` (Rejuv, buff, Bridge, mini-card, claims, `doScan`, objectives), then `runMaintenanceLane` (powerup rescans, linger, pretrack, monitor, prune).
  - Per-task cadence uses `isDue(task, nowMs, interval)` with `LAST_TICK`.
  - The next delay is `min(tick, minimapInterval, 500 ms)`; it is 250 ms while the Rift is hot and 100 ms (`TICK_FAST`) near a Rejuv spawn or during neutral overrides.
- The game clock comes from `gTime()`, which parses TopBar `.GameTime` and caches every valid value, including `0:00`, for 200 ms. It returns `-1` when no valid clock is readable.
  - An invalid clock is never treated as a rewind. While running, the loop skips its lanes and reschedules normally. While inactive, it retries after 1 s (`LOOP_INVALID_RETRY_MS`) and does not start a run.
  - A valid clock that jumps backwards, or reads 2 s or less after passing 30 s, triggers `reset(1)` and `startGeneration()`.
  - Below 10 s, a one-shot cleanup clears minimap state.
- `collectMinimapSnapshot()` classifies cached `map_button` panels into players, powerup spawns and the Rift warning.
  - Classification exits early in the order player → `powerup_spawn` → `capture_point`/`koth_warning`. The list comes from the `map_button` query, so the loop does not re-check that class. A panel that throws skips only its own marker.
  - The snapshot reuses its arrays and entry objects. The button query is cached for 800 ms.
  - Snapshot cadence is 250 ms (hot claim work), 500 ms (lingers active) or 750 ms (idle).
  - Claim, linger, pretrack, monitor and objective code consume this one snapshot; do not add another traversal.
- Powerup claims:
  1. Ten seconds before the Bridge respawn, pretrack accumulates the minimum squared ally/enemy distance to each known spawn.
  2. After the respawn, `scanPowerups` refreshes the spawns and starts `monitorPowerups`. A spawn's side comes from its x position (`xPct < 50`), then `invert_map`, never from its list index. If only one spawn is active, the other side keeps its last known position.
  3. When a spawn goes inactive, the nearest team within `CLAIM_RADIUS_SQ = 64` (in minimap percent²) claims it. Ties go to the ally. If no ally is close, the claim is attributed to the enemy.
  4. A dead player's `deadTs` is set only on the alive-to-dead transition. Stationary corpses stop counting after `DEATH_GRACE_MS`.
- Linger: `checkEnemyLinger` sees an enemy marker change from active to inactive and creates `LingerQ_<id>` under `BTLingerLayer`, a full-size, untransformed layer in `HudMinimapContainer` (it exists so `buff_claim.css` styles the labels). Positions are still computed against `HudMinimapContainer`. It saves the stock marker's hittest, opacity, input and focus state, then restores all of it on removal, death, reappearance, reset, retirement or any setup exception. The saved state is also stored as JSON in the marker's `bt_linger_prev` attribute, and a later instance reuses it, so restores stay correct across a script reload.
  - `computeLingerLabelPosition` places the marker inside `hud_minimap` by summing `actualxoffset`/`actualyoffset` along its `GetParent()` chain, mirrors it there for `invert_map` (that box is what gets flipped), then adds the `hud_minimap` offset inside `HudMinimapContainer`. Since 2026-09-29 that offset is the 30px gap between the 420px container and the 360px map. A broken chain falls back to the marker's own offset and the minimap's `actualxoffset`. Without live layout sizes, the marker's minimap fraction maps straight onto the container. The label takes the marker's width/height (container percent) and a font of 0.9 × marker height in layout pixels (via `actualuiscale_y`).
  - `showLinger` gets the minimap through `findMinimap()`. A quoted `UI["minimap"]` read here was undefined in the Closure build and caused the 30px offset seen in game on 2026-09-30.
- Rift:
  - `observeRiftMarker` accepts a `koth_warning` edge only once per interval and sets `_riftObservedSpawn = now + 20`.
  - `computeRiftState` returns text, sub, `inWindow`, `warning` and `confirmed`.
- Team chat:
  1. `TeamChatIntent.send` sanitises the message, applies a 300 ms cooldown and allows one in-flight intent at a time. The intent has its own token and expires after 2 s.
  2. It dispatches `say_chat_team`, then retries through `CHAT_RETRY_DELAYS` until `ChatInput` and a non-ALL `ChatTargetLabel` read ready twice in a row.
  3. `submitWithMinimalFocus` checks the token, the generation, the input and the team target again immediately before submitting. It refuses to overwrite a non-empty user draft. On every exit path it clears only the text it wrote and releases focus.

## Invariants

- Team signals: the perspective classes `friend` → 1 and `enemy` → 2 win. The legacy fallbacks `team1`/`ally` → 1 and `team2` → 2 apply only when neither is present. Stock `hud_minimap.css` uses `team1`/`team2` as absolute game-team colours (`.player.team1 #BackgroundImage`), so checking `team1` first classified Amber enemies as allies for Sapphire players (fixed 2026-10-08 from CSS evidence, not yet seen live). `client_cone_fov` is not a team signal.
- Class checks follow the casing current stock uses: `connectedToHideout` for the hideout and `PlayerDead` for dead players. If a game update changes the casing, update the check instead of adding variants.
- The cached `hud_minimap` panel's `invert_map` class is the only authority for orientation. It drives powerup sides and linger inversion. Do not fall back to `Players`, `Game` or a guessed default.
- A plain `capture_point` is present while idle. Only `.capture_point.koth_warning` means a Rift warning.
- Reserve `rift-confirmed` for an accepted warning at or before its observed spawn. A reappearing stale marker must not reactivate it. Keep estimated states muted, and limit the confirmed pulse to three stock-style cyan pulses.
- Rift uncertainty compounds by ±1m per unobserved interval. Do not replace it with fixed absolute anchors.
- During a neutral override, compute the mini-card Rejuv countdown from phase state. Do not mirror the overridden main label.
- Claim boxes stay in the widget layer, outside `minimap_persp`, so the scoreboard does not hide them. Linger labels stay in `BTLingerLayer` inside `HudMinimapContainer`, because `HudMinimap` does not reliably accept custom children.
- Widgets stay in their slots in `TimerOverlayFrame` (`.clamp_width`). Their default spots are the old percentage spots of the 440×440 box, measured from `BTTimerDock`, so untouched widgets follow the minimap. Hold Tab keeps them visible (only `hud.wants_scoreboard` changes); the big map covers them like the rest of the HUD layer (user decision 2026-10-09).
- Side glows stay inside `MinimapGlowClip`, a round 400px clip matching `minimap_frame`. Stock `minimap_container` has been a square clip with no radius since the 2026-09-29 update, so glows placed directly in `HudMinimapContainer` spill past the frame.
- Never add `hud.xml` back to pak98. New timer UI goes into an injected layout under an existing host.
- Minimap geometry is DPI-aware. When it is missing, use the live container extent, not desktop-sized constants.
- Reject all-chat targets. Chat must never gain authority beyond local UI.

## Settings and durable save

- Design agreed in a Claude / GPT-6.1-Sol debate (2026-10-08). The `/bt/` page reuses HP Colors v2's transport (request JSON in the URL fragment, reply in `HTMLTitle` with prefix `BTS1:`) but is a separate file with its own `VERSION` 1 and exactly one key, `hantu.bufftimer.v1/settings`. It has no backup key and no delete operation, and must never read, write or delete `hantu.hpcolors.v2/*`. The HP Colors root page and its protocol stay untouched. Same origin is not a security boundary: both pages can see each other's storage.
- Record: `BTS1.<fnv1a32>.<json>` with body `{"s":6,"u":"#RRGGBB","d":"#RRGGBB","l":0|1,"g":0|1,"t":{...},"c":{...},"k":10-150}`. `t` is optional and holds only moved widgets, in slot order: `"b"|"r"|"f"|"u"|"cl"|"cr": [x fraction, y fraction, scale 0.5-2, "l"|"r"|"t"|"b"]` (top-left as fractions of the layer, 4 decimals; claim boxes always store `"t"`; the Bridge and Rejuv pills may also store `"n"` = icon hidden), then `"m"`: the minimap size as a fraction 0.5-1.5, only when not 1, and `"mp"`: `[x, y]` top-left of the `#minimap_persp` box as layer fractions (5 decimals), only once moved or resized, then (schema 6) `"lc"`: `[dx, dy, degrees]`, the map location label's offset from its stock spot in minimap px (1 decimal, at most 1000) and its turn (-180 to 180; stock -30), only when not stock. Older builds read a schema 6 save as a newer save. `c` is optional and holds only changed colours: `a` ally claim, `e` enemy claim, `w` Weapon, `p` Spirit, `v` Vitality, `m` Movement glow (`#RRGGBB` uppercase). `k` (integer glow strength %) is present only when not 100. Schema 5 adds `b` (0 = borderless minimap, only when off), `o` (integer minimap opacity 20-100 %, only when not 100) (the one 2026-10-09 build with a minimap glow also wrote `h` and `c.h`; both are ignored on load and dropped on the next save). Any bad entry makes the record damaged. Schemas 3 (no `c`/`k`), 2 (no `t`) and 1 (palette build, indices 0-9 into `BT_PRESETS`, no `g`) still load and are rewritten as schema 5 on the next change. The worst case (all colours, strength, six widgets) stays under the page's 512 chars (tested). JSON keys and message fields are quoted in source so Closure keeps them.
- Store phases: `hello` (re-sent every 8 s, the last wait clamped to the 30 s deadline; accepted only for the latest hello id, exact page URL, version 1) → `read` (5 s timeout, one retry) → `ready`. A damaged or newer-schema record gives `blocked`: settings stay at defaults, edits are session-only, and only RESET clicked twice within 3 s overwrites it. Offline, untrusted or wrong-version pages give `unavailable` (session only for the whole process; nothing is written later).
- Controls are locked until the read settles. Saves throttle 1.5 s, closing the menu sends a pending save at once (an untouched menu writes nothing), unchanged records are skipped, one write is in flight and its ack reschedules a newer value; a failed write retries after 2/4/8 s, then the session becomes `unavailable`.
- Two contexts, designed in a second Claude / GPT-6.1-Sol debate (2026-10-08) because most mods replace `hud.xml`:
  - `bt_minimap_settings.js` walks `GetParent()` from the minimap to the first `.HudCore` ancestor (fallback `paneltype` `CitadelHud`; retries every 1 s) and creates `Panel#BTMinimapSettingsHost` there, outside the minimap's clip and its `.invert_map` mirror, then `BLoadLayout("file://{resources}/layout/bt_minimap_settings.xml", false, false)` (up to 3 tries 5 s apart; the arrows still paint without it). The layout has no script and no `onactivate`; every handler is bound with `SetPanelEvent`.
  - Generation guard: each boot increments the int attribute `bt_settings_gen` on that ancestor and deletes older direct-child hosts. Every schedule and event handler checks `alive()` (context valid, ancestor valid, attribute still equals its generation), and the first failed check cancels every handle, so a reloaded minimap never leaves two stores or loops running.
  - The two scripts share classes on `#hud_minimap` and the timer's `$["BTTimerLayout"]` API. The settings script sets `bt-linger-off` / `bt-glow-off`. `readSettingsContract()` runs once at the top of every live timer `loop` tick, before the invalid-clock and hideout returns. It sets `bt-buff-timer`, mirrors `bt-glow-off` onto `MinimapGlowClip`, and calls `clearAllLingers()` when `bt-linger-off` appears. Without `bt-buff-timer` the menu gets `no-buff-timer`, which hides the timer-owned rows. No class means linger and glow on.
  - Colours and strength: once the save is read, the settings loop sends `look({a,e,w,p,v,m: "#RRGGBB", k: 10-150})` (only when changed or after a timer reboot). The timer then paints inline over the CSS: glow `background-color` gradients from the buff class (or `e` during the 3 s enemy flash; strength k dims every alpha below 100 and above 100 raises the mid stop and moves the fade from 60% to 85% of the panel), and claim `#ClaimBg*` gradient/border plus ring `border-color` from `a`/`e` (live claim or edit-mode sample). Writes are cached per panel; until a look arrives the CSS colours apply.
  - The timer's own writes (`bt-buff-timer` per minimap panel, `bt-glow-off` per glow host and value) are cached by panel identity. The two settings classes are still read every tick.
  - The settings menu re-renders only on events: open/close, settings changes, status, editor sync, hydration, reset arming or expiry, and host binding. ## Coding conventions

- Use two-space indentation, `UPPER_SNAKE_CASE` constants, `camelCase` state and functions, and `_prefixed` caches. Keep the strict IIFE.
- Cache panels at boot or first discovery, and validate them with `?.IsValid?.()`/`panelValid()` before use. Wrap engine calls in narrow `try/catch`.
- Every recurring write goes through `WRITE_CACHE`: `writeText`, `writePanelStyle`, `setObjectiveCardClass` or `setMiniCardState`. Do not reassign unchanged text, classes, images or styles.
- In recurring work, reuse arrays and objects, compare squared distances, and avoid new full-tree traversals.
- Every `$.Schedule` handle that can outlive state must be cancellable or generation-checked.
- Mutations of stock panels are transactional: capture, apply, then roll back through the normal removal path.
- Engine-owned properties (`"hittest"`, `"hittestchildren"`, `"BAcceptsInput"`, `btn["id"]`, …) use quoted bracket access so Closure ADVANCED does not rename them. Injected layouts carry no `onactivate`; bind handlers with `panel["SetPanelEvent"]`, guarded by `timerAlive()`.
- Script-owned caches (`UI.*`, `State`-style objects) are the opposite: always dotted, never quoted. Closure renames dotted names, so mixing `UI.x` and `UI["x"]` reads `undefined` only in the shipped build, where the unminified validators cannot see it. `validate-runtime-engine.js` rejects any `UI["…"]` access.
- Tables read with a runtime string (`LAYOUT_BASE[spec.kind]["h"]`) need quoted keys. Closure renames bare keys (`pill` became `Eb`), so the lookup returns `undefined` only in the shipped build. `validate-closure-layout.js` catches this for the layout code.
- The same rule in reverse: never reach a dotted/bare field through a string (`owner[key]` helpers, string-keyed loops, bare-key `Object.assign` onto a quoted table). Until 2026-10-09 `cancelScheduledHandle(side, "claimTimeout")`, retire's `["enemyGlowHandle", "animHandle", "claimTimeout"]` loop and `Object.assign(NEUTRAL_ACTIVE, { bot: false, … })` did nothing in the shipped build (claim and enemy-glow schedules were never cancelled; a reset left the quoted neutral flags set). Use `x = cancelScheduled(x)` on dotted fields. Check: `BT_SOURCE_ROOT=buff_timer_virgin_closure/panorama node buff_timer_virgin/scripts/measure-buff-timer.js` must give the same observed digests as the source run.
- The XML IDs, `PANEL_IDS`, CSS selectors, Closure externs and validator mocks are one contract. Change them together.
- Engine style setter (panorama.dll, client 6763): `null` clears a base property but throws for an alias ("Cannot set a property alias to undefined"); `""` always throws. `horizontalAlign`/`verticalAlign` are aliases of `align`, `uiScaleX/Y/Z` of `uiScale`; clear `align`/`uiScale` instead. Clearing an inline `visibility: collapse` with `null` did not show the panel again in game; write `"visible"`. `bt-test-harness.js` (`engineStyle`) models all three.
- Panorama CSS is not browser CSS. Use `visibility: collapse`, `overflow: noclip`, `pre-transform-scale2d` and `style.clip`. Animate opacity only; do not use `box-shadow` or `clip-path`.
- Production must not log. Debug output goes through `dbgPing` behind `DEBUG_PING_TIMER = false`. Closure ADVANCED checks call arity, so optional parameters need a JSDoc `{type=}` annotation. The build must finish with 0 Closure warnings.
- Performance work follows `.agents/skills/optimize-measured/SKILL.md` and `refactor-pinned/SKILL.md`:
  - `scripts/measure-buff-timer.js --output <file>` boots both scripts in one VM context against a mock HUD (1600×900 at ui scale 0.8333, with window positions, so layout placement and look painting really run). Over ten scenarios it reports calls into the game per second, attributed to each script, plus a digest of every observed output. `customLookClaim` loads a saved schema 4 record (moved widgets, picked colours, strength 140) and paints an ally and an enemy claim; `layoutEditDrag` moves, flips and resizes widgets and drags the edit box during a match, then DONE. `BT_SOURCE_ROOT=<copied panorama dir>` runs the same harness on an old tree for equivalence, `BT_PROFILE=<file>` adds per-function counts, and `BT_PROFILE_DEPTH=2` names the caller's caller (for shared helpers such as `panelValid`).
  - Do not cache map_button team, id or type across snapshots without engine evidence that panels are never reused; the snapshot deliberately re-reads them.
  - The 2026-10-08 round's before/after artifacts are `.scratch/bt_opt_1008/baseline.json` and `after.json`; the 2026-10-09 round's are `.scratch/bt_refactor_opt/baseline.json` and `after.json`.

## Commands

Run from the repository root:

```powershell
node buff_timer_virgin/scripts/validate-runtime-engine.js
node buff_timer_virgin/scripts/validate-team-chat-intent.js
node buff_timer_virgin/scripts/validate-settings-store.js
node buff_timer_virgin/scripts/validate-layout-editor.js

powershell -ExecutionPolicy Bypass -File build_buff_timer_virgin.ps1 -SkipDeploy  # stop after VPK assertions
```

The wrapper runs these steps:

1. Run all five validators.
2. Stage `panorama/` in `buff_timer_virgin_closure/` and strip the `// TEST_EXPORTS_BEGIN` … `// TEST_EXPORTS_END` block from both scripts. The markers are required, and the build fails if they are missing.
3. Run `npx --yes google-closure-compiler` in ADVANCED mode separately for `rejuvnbufftimer.js` and `bt_minimap_settings.js`, each with its own generated externs. Fail on a nonzero exit or any `WARNING - ` line, and assert the handler names, store URL, host ID, layout path and contract classes survive. Then run `validate-closure-layout.js` on the two minified scripts.
4. Compile the eleven assets with `sr2compiler/New folder.exe`: two scripts, five layouts (`hud_minimap`, `bt_minimap_settings` and the three timer layouts) and four stylesheets (`hud_timer`, `buff_claim`, `bt_minimap_arrows`, `bt_minimap_settings`).
5. Pack pak98 with `vpkeditcli.exe`, then assert that the eleven assets are present and that the validator scripts, `hud.vxml_c`, `bt_claim_overlay.vxml_c` and `hud_minimap.vcss_c` are not.
6. Deploy to `G:\SteamLibrary\steamapps\common\Deadlock\game\citadel\addons\pak98_dir.vpk`, unless `-SkipDeploy` is passed.

The compiler may exit nonzero after producing output. The wrapper's required-output check decides success. There is no lint step and no package runner.
